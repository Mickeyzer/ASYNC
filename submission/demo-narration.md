# Three-minute demo rehearsal guide

Use a clean synthetic customer account and four documents from the same applicant. Select the applicant after independent live validation, not from the judges-only pack. Do not claim that a failed or unclear applicant should pass. Keep the simulation banner visible.

| Time | Show | Explain |
| --- | --- | --- |
| 0:00-0:25 | Visible registration, business description and reviewed follow-up | Explain how a short reply updates the draft and retains reviewed facts. Hindi is available; demonstrate voice only on a verified device with separate consent. |
| 0:25-0:50 | Recommended bundle and edits | Backend eligibility/dependency checks, per-service contracts and itemized monthly/setup fees; owner can change quantities. |
| 0:50-1:10 | Reviewed estimate and account-bound document consent | Show the price and explain provider processing, masking and retention. |
| 1:10-1:45 | Four document uploads and checks | Live extraction feeds deterministic mock-registry, date and consistency checks. Briefly show one genuine correction case or use a prevalidated second applicant. |
| 1:45-2:05 | Explicit demo checkout and saved tracker | One idempotent order; no real payment or service activation. Explain recovery through account sign-in. |
| 2:05-2:35 | Owner-requested follow-up and partner queue | Consent precedes contact sharing. Reviewers assign tasks; partners see assigned summaries. Hard failures remain blocked. |
| 2:35-2:55 | Account controls, Hindi metrics and channel status | Show session revocation/password controls, then distinguish unique journeys from retries. WhatsApp guided replies are locally tested; live sending is disabled. Pilot targets remain proposals. |
| 2:55-3:00 | Limits | Name the simulated integrations and remaining live/deployment gates. |

If provider latency prevents a complete live run within the limit, make an honest recording with labelled cuts and elapsed processing times. Do not substitute fixture results without visibly labelling them. The supplied short rehearsal is labelled as controlled fixtures and is not a live-provider result; its measured duration is in demo-manifest.json.

Prepare answers on: why backend code controls prices, how reviewed facts differ from chat, password/session revocation, consent withdrawal and STOP, evidence expiry, staff permissions, the rejected acquisition heuristic and how a pilot would test the assumptions. Do not call the extra features proof of production readiness.
